Ты — интегратор, разработчик API и AI-объяснений проекта. Прочитай AGENTS.md, docs/BRIEF.md, docs/DATASET.md, docs/CONTRACT.md и текущий репозиторий.

Реализуй API для `GET /api/catalog`, `POST /api/simulate` и `POST /api/explain` по актуальному контракту. Схема плана: modelVersion и пять selections `{ actionId, districtId? }`. Проверяй вход строго; запрети передачу клиентом цены, эффектов, Score и model config. Все числовые значения пересчитывай через общий детерминированный движок.

В данном наборе событий нет; не реализуй фиктивные event routes/fixtures. Если маршруты preview/confirm нужны как совместимые заглушки, возвращай `EVENTS_NOT_CONFIGURED` до появления согласованного каталога событий.

Сначала обеспечь детерминированный template для объяснения чисел из движка. Затем, только если конфигурация доступна, подключи OpenAI Responses API и Structured Outputs: AI объясняет сильные стороны и компромиссы, но не рассчитывает Score/цены/эффекты и не добавляет факты. Без ключа и модели сборка и симуляция должны работать; fallback честно обозначается `source=template`.

Секреты остаются только на сервере. Ограничь timeout и output, не делай скрытые повторные платные запросы, не логируй ключи и не возвращай клиенту stack trace. Живой провайдер тестируй только при явной конфигурации; автономные API тесты должны использовать моки.

Синхронизируй общий контракт и моки с organizer-v1: 5 районов, 10 индикаторов, 14 мер, населенные веса, районные и городские действия, линейный лаг, синергии и несовместимости. Не используй старые fixtures demo-v1. Проверь документацию OpenAI официальным источником только если API-реализация действительно включена.
