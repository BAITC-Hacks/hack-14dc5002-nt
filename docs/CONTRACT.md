# Общий контракт v1

Источник типов: src/contracts/index.ts. Источник данных: src/data/catalog.json. Примеры HTTP-ответов: src/mocks/*.json; все они используют envelope ApiResponse<T>. Это фиксированные тестовые примеры, не реализация API.

## API
| Метод и путь | Тело запроса | data успешного ответа |
|---|---|---|
| GET /api/catalog | нет | Catalog |
| POST /api/simulate | PlanInput | SimulationResult |
| POST /api/events/preview | EventPreviewInput | EventPreviewResult |
| POST /api/events/confirm | EventConfirmInput | EventConfirmResult |
| POST /api/explain | ExplainInput | Explanation |

400 — неверная JSON-форма/лишние поля; 409 — несовместимая modelVersion; 422 — недопустимое событие/подтверждение/объяснение; 429 — ограничение запросов; 500 — обезличенная ошибка сервера. Невалидный по количеству/бюджету обычный план на /simulate возвращает HTTP 200, ok=true, но data.valid=false и officialScore=null. Это нормальное состояние редактора, а не ошибка сервера.

Все схемы входа строгие. Принимать от клиента стоимость, эффекты, доступность, готовый Score и model config запрещено. Версию модели сверять с серверной. Порядок actionIds не влияет на результат; нормализуй сортировку перед расчетом и кэшированием, не мутируя вход. Максимальный размер входного списка ограничить небольшим числом, например 30.

## Экспорты движка (участник 2)
Файл src/lib/simulation/index.ts экспортирует:
```ts
validatePlan(plan: PlanInput, catalog: Catalog, eventId?: string): ValidationIssue[]
simulatePlan(plan: PlanInput, catalog: Catalog, eventId?: string): SimulationResult
previewEvent(input: EventPreviewInput, catalog: Catalog): EventPreviewResult
confirmEvent(input: EventConfirmInput, catalog: Catalog): EventConfirmResult
```
Также экспортируй DomainError extends Error с полями code: string и issues: ValidationIssue[]. previewEvent/confirmEvent бросают DomainError при недопустимом переходе. Сервер передает eventId в расчет ветки только после проверки события; /simulate не принимает eventId от клиента и рассчитывает обычный исходный план.

## Клиентский адаптер (участник 3)
Файл src/lib/client-api.ts экспортирует асинхронные getCatalog(), simulate(plan), previewEvent(input), confirmEvent(input), explain(input). Каждая возвращает Promise<ApiResponse<T>> согласно таблице. При сетевой ошибке также возвращает ok=false с code=NETWORK_ERROR, не падает необработанным исключением. Mock-режим использует те же типы/формы, но только для перечисленных fixtures. На неизвестный mock-запрос возвращай понятную ошибку, НЕ подставляй результат чужого плана. Финальное демо работает с mock-флагом false.

## Чистая математика
Для каждого района d и показателя k:
active(a) = 1, если horizonMonths >= a.lagMonths, иначе 0.
X[d,k] = clamp(baseline[d,k] + sum(active(a) * effects[a,d,k]), 0, 100).
Absent effect = 0. Ограничение применяется один раз после суммы, не по одному действию.
DistrictScore[d] = sum(dimensionWeight[k] * X[d,k]).
CityDimension[k] = sum(districtWeight[d] * X[d,k]).
Score = sum(districtWeight[d] * DistrictScore[d]).
В обоих наборах веса неотрицательны и в сумме равны 1. Каталог проверяется один раз при загрузке. Все числа конечные, стоимость неотрицательна, лаг неотрицателен; ID уникальны; ссылки на районы/действия/события существуют.

В API числа не округляются. UI отображает один знак после запятой. Сравнение использует исходную точность; для ранжирования Score нормализуется до 9 знаков (числовой ключ Math.round(score * 1e9)), чтобы погрешность float не ломала правило равенства; тесты разных реализаций сравнивают дроби с tolerance 1e-6. trace показывает примененные сырые вклады до итогового clamp: не выдавай их за независимые предельные вклады после насыщения.

Для невалидного плана totalCost — сумма стоимостей уникальных известных ID; remainingBudget = limit - totalCost (может быть отрицательным). Неизвестные ID/дубликаты все равно дают ошибки и никогда не Score. Нет расчета metrics/trace для невалидного плана.

## Ограничения
Ровно пять уникальных ID; бюджет <=100; известная версия; каждое мероприятие доступно; requires присутствуют; excludes не присутствуют. Конфликт проверяется в обе стороны. Не выбирай event-only мероприятие до его события. Заблокированное событием мероприятие недоступно во всей ветке. Никакого требования покрыть все направления по одному действию.

## Событие отмены
previewEvent проверяет базовую пятерку обычным контекстом. Событие применимо, только если blockedActionId входит в базовый план. base — пересчитанный неизменяемый исходный результат. draft — копия без отмененного действия; draftResult.valid=false, officialScore=null. Освободившийся бюджет = 100 - стоимость draft.

Для каждой доступной альтернативы, которой нет в базе: собрать draft + кандидат; полностью проверить ограничения; рассчитать пятерку. Только валидные варианты включать в replacementOptions. Сортировка: ключ Math.round(officialScore * 1e9) по убыванию, totalCost по возрастанию, addedActionId и затем removedActionId лексикографически. Вернуть максимум три. Пустой список — честное состояние «допустимых замен нет», не выдумывать мероприятие.

confirmEvent не доверяет присланным прогнозам и не зависит от server-memory/session state. Повторно проверяет basePlan, событие и пару ID. removedActionId строго равен blockedActionId; addedActionId доступен, не входит в базу, не заблокирован. Новый план = base - removed + added. Валидатор вновь проверяет ровно пять и бюджет. Можно подтвердить любой допустимый одиночный swap, не только top-3, но обязательно в рамках события. Возвращает base, branch и comparison. Входные объекты не мутируются.

## Новая возможность
Новое действие заранее описано в каталоге с availability.kind=event и eventId. previewEvent не добавляет его шестым: draft пока равен исходной пятерке, draftResult формально валиден, requiresReplacement=true. Перебрать пять вариантов замены каждого старого на unlockedActionId, оставить до трех допустимых по той же сортировке. confirmEvent требует addedActionId=unlockedActionId и removedActionId из базовой пятерки. Нельзя подтвердить неизмененный план или использовать другое открытое событие.

## Клиентское состояние
Раздельно хранить draft исходного плана, baseSnapshot и eventBranch. Снимок сохраняется после успешной базовой симуляции. Изменения draft снимают актуальность его результата, но не мутируют уже сохраненный baseSnapshot. Новая базовая симуляция явным образом создает новый snapshot и сбрасывает предыдущую ветку. Событие работает только от активного snapshot. Переходы: editing → simulated → eventPreview → eventConfirmed.

Ветку до подтверждения нельзя показывать как утвержденный результат. Результат кандидата подписывать «предварительный результат после замены», а не «Score плана из четырех». При изменении выбора сбрасывать старый preview и поздние AI-ответы; привязывать запросы к версии/хэшу плана или счетчику запроса, использовать AbortController где доступно. Кнопку подтверждения блокировать при отправке. После перезагрузки восстановить snapshot из localStorage и проверить актуальность modelVersion; сервер пересчитывает цифры из ID перед сравнением/AI.

## Объяснения
/explain принимает только ExplainInput. Сервер заново вызывает simulatePlan или confirmEvent и строит проверяемые факты. Модель получает факты, а не право менять данные. Использовать Responses API Structured Outputs с runtime-схемой Explanation без поля source (source добавляет сервер). Проверять все actionIds/districtIds ответа по переданным данным. Предпочтительны качественные пояснения: числовые карточки и дельты рисует UI напрямую из движка. Нельзя выдавать причинную модель за подтвержденный прогноз города.

Не более одного вызова для зафиксированного базового результата и одного для подтвержденной ветки в обычном демо-пути. Не вызывать AI для каждого кандидата или при каждом нажатии на карточку. Серверный кэш необязателен, но при его наличии включить в ключ canonical plan IDs, modelVersion, событие/swap, горизонт, AI model, язык и версию промпта. Нельзя считать in-memory кэш/лимит надежным межсерверным хранилищем или глобальным ограничителем расходов.

Timeout около 12 секунд, небольшой max_output_tokens, без скрытых повторных запросов. AI_ENABLED=false, отсутствующий ключ/модель, timeout, отказ, ошибка или неправильный ответ → детерминированное объяснение source=template. OpenAI-клиент создается только внутри серверного запроса при наличии конфигурации, не на этапе импорта/сборки. Логи не содержат ключи, тело исключения провайдера не отправляется клиенту. Перед публичным размещением AI endpoint защитить доступом/серверным лимитом; без такой защиты демонстрировать локально либо выключить AI на публичной копии.
